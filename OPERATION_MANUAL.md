# Operation Manual - SRAM PUF Key Generator (STM32H533 / NUCLEO-H533RE)

This manual explains how to set up, run and evaluate the project. There are two
evaluation paths:

- **Path A - No hardware (about 5 minutes).** Runs the real firmware crypto code on a PC
  against a simulated SRAM PUF and checks the whole pipeline automatically.
- **Path B - With the NUCLEO-H533RE board.** Collects real SRAM power-up data, enrolls,
  and reconstructs the key on the device.

## 1. What the system does

An SRAM PUF uses the random power-up state of on-chip SRAM cells as a chip-unique
fingerprint. The fingerprint is noisy, so a fuzzy extractor turns it into a stable key:

1. `enroll.py` measures which cells are stable, selects 3840 of them, and creates public
   *helper data* (`helper_data.h`).
2. At every boot, the firmware reads the SRAM, combines it with the helper data, corrects
   errors by majority vote (15 cells per secret bit, 256 bits), hashes the result with
   SHA-256, and checks it against a stored hash.
3. No key is stored in flash. Only public helper data is.

## 2. Repository layout

| Path | Purpose |
|---|---|
| `firmware/Core/Src/puf_fe.c` | Fuzzy extractor (reconstruction) |
| `firmware/Core/Src/puf_app.c` | Early SRAM snapshot, capture mode, key mode |
| `firmware/Core/Src/sha256.c` | SHA-256 implementation |
| `firmware/Core/Inc/puf_config.h` | Mode, SRAM addresses, code parameters |
| `firmware/Core/Inc/helper_data.h` | Generated by `enroll.py` (placeholder until enrolled) |
| `firmware/linker_memory_snippet.ld` | Linker `MEMORY` block that keeps SRAM2/3 untouched |
| `host/capture.py` | Collects SRAM dumps over the ST-LINK virtual COM port |
| `host/analyze.py` | PUF quality metrics |
| `host/enroll.py` | Stable-cell selection, helper data, held-out validation |
| `host/sim_puf.py` | Simulated PUF (for testing without hardware) |
| `tests/run_tests.sh`, `tests/test_host.c` | Automated end-to-end test |

## 3. Path A - Evaluate without hardware

### Requirements
- Linux, macOS, or Windows with **WSL** (or Git Bash with MinGW gcc)
- `gcc`, `python3`, and `pip install numpy pyserial`

### Procedure
```bash
git clone https://github.com/Kasinath20/sram-puf-stm32.git
cd sram-puf-stm32
pip install -r host/requirements.txt
bash tests/run_tests.sh
```

### What the test does
1. Checks the firmware's SHA-256 against Python `hashlib`.
2. Simulates a chip with 60 power-ups, then runs `enroll.py` (which validates on held-out boots).
3. Builds the **actual firmware files** `puf_fe.c` and `sha256.c` for the PC.
4. Feeds 200 new simulated boots of the same chip and requires the same key each time.
5. Feeds 20 boots of a different simulated chip and requires that all are rejected.

### Expected output (numbers vary slightly, since noise is random)
```
== 1. SHA-256 vs Python hashlib
  ok ... (3 lines)
[validation] key reconstruction success: 18/18
[enroll] KEY FINGERPRINT (device should print this): xxxxxxxx
  reconstruction success: 200/200
  false accepts: 0/20
ALL TESTS PASSED
```
Path A passing means the algorithm and code are correct. It does not prove behaviour on
real silicon, which Path B does.

## 4. Path B - Run on the NUCLEO-H533RE

### 4.1 Requirements
- NUCLEO-H533RE board and a **data** USB cable
- STM32CubeMX and STM32CubeIDE (free, from st.com)
- Python 3 with `pip install -r host/requirements.txt`
- A serial terminal (for example PuTTY) for the final check

### 4.2 Create the CubeIDE project
1. In **STM32CubeMX**: *File -> New Project -> Board Selector*, select `NUCLEO-H533RE`,
   answer **Yes** to default peripherals, and keep **TrustZone off**.
2. In *Project Manager*, name the project `sram_puf`, set **Toolchain/IDE = STM32CubeIDE**,
   and click **Generate Code**.
3. In CubeIDE: *File -> STM32 Project Create/Import -> Import STM32 Project ->
   STM32CubeMX/STM32CubeIDE Project*, and select the generated folder.
4. Open `sram_puf.ioc -> Connectivity` and note which USART is the ST-LINK virtual COM port
   (for example `USART3`, handle `huart3`).

### 4.3 Add the PUF code
1. Copy `firmware/Core/Inc/*` into the project's `Core/Inc/` and `firmware/Core/Src/*` into `Core/Src/`.
2. Open `STM32H533RETX_FLASH.ld` and replace the `MEMORY { ... }` block with the contents
   of `firmware/linker_memory_snippet.ld` (firmware then uses only SRAM1).
3. Edit `Core/Src/main.c`. Put each line **inside the matching `USER CODE` block**:
```c
/* USER CODE BEGIN Includes */
#include "puf_app.h"
/* USER CODE END Includes */

int main(void)
{
  /* USER CODE BEGIN 1 */
  puf_snapshot_early();          /* must be BEFORE HAL_Init() */
  /* USER CODE END 1 */
  ...
  /* USER CODE BEGIN 2 */
  puf_app_run(&huart3);          /* use your VCP handle; never returns */
  /* USER CODE END 2 */
```
4. Build (*Project -> Build All*). It must finish with 0 errors.
5. After building, open the generated `.map` file and confirm nothing is placed at
   `0x20020000` or above.

### 4.4 Phase 1 - Collect real SRAM data
1. Make sure `PUF_MODE` is `PUF_MODE_CAPTURE` (the default in `puf_config.h`).
2. Flash with **Run**. The board waits for the host.
3. Start collection:
   ```bash
   python host/capture.py --n 100
   ```
4. For each capture the script asks you to **unplug the USB cable, wait 5 s, and plug it in
   again**. A true power cycle is required. The reset button and debugger resets keep SRAM contents.
5. Dumps are saved in `captures/`. Vary conditions for some of them (different USB port,
   the room warmed or cooled).
6. Check quality of each bank:
   ```bash
   python host/analyze.py 20020000
   python host/analyze.py 20034000
   ```
   Good result: uniformity about 0.5 and a bit error rate of a few percent. If a bank is all
   zeros or all ones, it is erased or ECC-initialised, so use the other bank.

### 4.5 Phase 2 - Enroll and reconstruct
1. Generate helper data from the good bank:
   ```bash
   python host/enroll.py --dir captures --addr 20020000 --out firmware/Core/Inc/helper_data.h
   ```
   Note the `KEY FINGERPRINT` and the `[validation]` results. Validation should show
   success on all held-out boots.
2. In `puf_config.h` set `PUF_MODE` to `PUF_MODE_KEY` (or add the compiler symbol `-DPUF_MODE=1`).
   If you enrolled SRAM3 (`20034000`), also set `PUF_KEY_REGION 1`.
3. Rebuild and flash. Then **unplug and replug USB** (a true power-up).
4. Open a serial terminal at **115200 baud, 8N1** on the ST-LINK port.

### 4.6 Expected result
```
KEY_OK fp=xxxxxxxx corrected=N worst_group=M rsr=0x........
```
- `fp` must equal the fingerprint printed by `enroll.py`.
- `corrected` is the number of bit errors fixed on this boot.
- `worst_group` is the worst case out of 15 cells per bit. Reconstruction fails at 8 or more.
- The green/yellow LED toggles once per second on success.

Repeat with 20 or more power cycles and record how many give `KEY_OK` with the same `fp`.

`KEY_FAIL code=3` means too many bit errors. Fix: collect more captures and re-enroll, or
increase `PUF_GROUP_N` in both `puf_config.h` and `host/enroll.py`.

## 5. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| No serial port appears | Charge-only cable, or ST-LINK driver not installed |
| No output, no LED | Wrong SRAM address (HardFault) or wrong UART handle in `puf_app_run(&huartX)` |
| Garbage or CRC errors | Baud rate differs from the CubeMX USART setting (default 115200) |
| Dumps are all 0x00 or 0xFF | Bank is erased or ECC-initialised: use the other bank; check option bytes in STM32CubeProgrammer |
| Dumps identical every time | Not a real power-up (a reset was used): fully unplug USB |
| Compile error `RCC_RSR_RMVF` or `LD2_Pin` | Name differs in your HAL version: check the device header / `main.h` |
| `KEY_FAIL code=1` | `helper_data.h` is still the placeholder: run `enroll.py` |
| `KEY_FAIL code=2` | Mask does not have exactly 3840 cells: regenerate with `enroll.py` |

## 6. Known limitations
- Verified on simulated data. Real-hardware results must be collected with Path B.
- Only one board is available, so inter-chip uniqueness cannot be measured.
- The repetition code leaks some entropy through public helper data. This is acceptable for a
  prototype, and a production design would use a stronger code and an entropy budget.
- Helper data is not authenticated, so helper-data manipulation attacks are out of scope.
- SRAM PUF behaviour changes with aging, temperature and voltage.
- Raw SRAM dumps are the device's fingerprint and are deliberately excluded from the repository (`.gitignore`).
